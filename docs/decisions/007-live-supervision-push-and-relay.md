# 007 — Live supervision, push notifications and phone-to-phone relay

**Status:** accepted (27 Nov 2026)

**Live positions from heartbeats plus synced GPS.** Phones on shift send a tiny heartbeat every 3 min (position, battery, unsynced count) — one row per user, overwritten, and a delayed older beat never replaces a newer one. `GET /team/live` takes the newest of the heartbeat and the latest synced GPS point. Status (moving / at point / idle / off shift / no signal) is computed on the server from thresholds in campaign config `live`, so every screen agrees. We chose polling (map every 30 s, home every 60 s) over websockets: simpler, works through bad networks, and a supervisor of 2–10 collectors needs nothing faster.

**Push via Expo, written transactionally.** A notification is a row in `notifications` created in the same transaction as what it announces (flag, message, reassignment); it is sent after commit, so a rolled-back request never notifies. A `dedupe_key` makes alerts idempotent (the same flag or the same silent stretch notifies once). Messages are notified from one SQLAlchemy `before_flush` listener, so every path that creates a message (flag actions, revisits, replies, broadcasts, phone pushes) is covered. Expo's push service wraps FCM with one HTTP call and no server-side Firebase credentials; FCM credentials live in Expo. Push is optional: without the Firebase/Expo setup, builds still work and the app raises local notifications for new high flags while open.

**Phone-to-phone: animated QR, not Nearby Connections.** The spec suggested Android Nearby Connections. For the pilot we use QR codes cycling on the collector's screen, scanned by the supervisor's camera: no pairing, no Bluetooth/Wi-Fi/location permission prompts, no native module to maintain, works on any phone with a camera, and both users can see it working. A typical day's work records (a few KB compressed) take 5–20 codes, a few seconds. GPS tracks are left out (too large) and arrive with the collector's own sync. Nearby Connections can replace the transport later without changing the bundle format.

**Bundles are sealed for the server, not for the supervisor.** Each collector has a random 32-byte relay key, fetched once while online and kept in the phone's secure store. The bundle is ChaCha20-Poly1305 over zlib(JSON push body), with the collector id as associated data; the supervisor's phone stores and forwards it but can neither read nor alter it, and a bundle can't be replayed as another collector. The server checks that the carrier supervises the collector, opens the bundle and stores the records through the same `apply_records` code as a normal sync — so idempotency, validation and flag processing are identical, and a later direct sync of the same records is acknowledged as a duplicate. Records stay queued on the collector's phone until it syncs itself, so a lost supervisor phone loses nothing. The clock-offset check uses the time the supervisor scanned the bundle, not when it reached the server.

**Reassignment** moves only points nobody has started (pending / en route / arrived), within one team; work already collected stays with whoever collected it.

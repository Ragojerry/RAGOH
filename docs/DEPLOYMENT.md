# Deployment

RAGOH staging runs in **pilot mode** (see ARCHITECTURE.md §3.3): one EC2 server in **eu-north-1 (Stockholm)** running the API, PostgreSQL/PostGIS, Redis and Caddy (automatic HTTPS) with `docker compose`.

## How a deploy happens

Merging a pull request into `main` triggers **.github/workflows/deploy.yml**:

1. **CI** — lint, type checks, tests against PostGIS, migration check, Docker build, Terraform validate.
2. **Terraform apply** (`infra/terraform/envs/staging`) — signs in to AWS with GitHub OIDC (role `ragoh-github-deploy`), creates or updates the server, registry, buckets and secrets. State lives in `s3://ragoh-tfstate-568898409880-eu-north-1/staging/terraform.tfstate`.
3. **Build & push** the API image to ECR (`ragoh-api:<commit>`).
4. **Upload** `deploy/staging/` to the deploy bucket.
5. **Roll out** with AWS Systems Manager: the server pulls the bundle and runs `deploy.sh`, which writes `.env` from Parameter Store, pulls the new image and restarts the stack. Migrations and seed data run automatically when the API starts.
6. **Smoke test** — `GET https://<host>/health` must return `{"status":"ok"}` and the dashboard must load at `https://<host>/`.

The web dashboard (`apps/web`) is built in the same run and served by Caddy at the site root; the API stays under `/api` and its docs at `/docs`.

The run summary (GitHub → Actions → the Deploy run) shows the staging URL. You can also re-run a deploy manually: Actions → Deploy → **Run workflow**.

## The first deploy

The first run creates everything, so it takes longer (~10–15 minutes): the server boots, installs Docker, registers with Systems Manager, and Caddy obtains an HTTPS certificate.

## Road routing and offline map (one-time, after the first deploy)

1. GitHub → **Actions** → **Routing data** → **Run workflow** (on `main`). It takes ~15–25 minutes and builds the FCT walking network and offline map from OpenStreetMap.
2. When it finishes, run **Deploy** again (Actions → Deploy → Run workflow) so the server picks up the data.
3. Check: `https://<host>/api/v1/map/style.json` now returns a style (not 404), and route answers in `/docs` say `"source": "osrm"` / `"vroom"`.

It re-runs automatically on the 2nd of each month to pick up map changes (then re-run Deploy, or wait for the next merge).

## Logging in to staging

- URL: shown in the Deploy run summary, e.g. `https://13-48-10-20.sslip.io` — the **supervisor dashboard** opens there (see DASHBOARD.md); API docs at `/docs`.
- Users: `admin` (administrator); `sup1`, `sup2` (supervisors); `col1`–`col4` (collectors).
- Passwords are generated by Terraform and never stored in the repo. Find them in **AWS Console → Systems Manager → Parameter Store** (region eu-north-1):
  - `/ragoh/staging/ADMIN_PASSWORD` → for `admin`
  - `/ragoh/staging/DEMO_PASSWORD` → for `sup1`, `sup2`, `col1`–`col4`
  
  Open the parameter and click **Show decrypted value**.

Try it in the browser at `https://<host>/docs`: `POST /api/v1/auth/login` → copy `access_token` → **Authorize** → call other endpoints.

## Demo data

Staging is seeded with an FCT pilot: the FCT and its six area councils (**approximate rectangles — replace with official boundaries** via `POST /api/v1/admin-areas/import`), the campaign "FCT Pilot Survey", Team AMAC (sup1, col1, col2) and Team Bwari (sup2, col3, col4), and 120 demo households assigned to the collectors.

## Uploading visit points

`POST /api/v1/visit-points/import` (admin or manager), form fields `campaign_id`, `file` (.csv/.xlsx/.geojson), optional `dry_run=true` to check a file without saving. Required columns: `external_id, name, lat, lon`; optional: `type, admin_area_code, priority, geofence_m, window_start, window_end, planned_date, collector`. Extra columns are kept as attributes. Re-uploading updates existing points instead of duplicating them.

|---|---|

| Restart the API | Same session → `sudo docker compose restart api` |
| Database backups | Nightly at 02:15 to `s3://ragoh-staging-backups-568898409880/postgres/`, kept 30 days |
| Restore a backup | Session → `aws s3 cp s3://…/postgres/ragoh-YYYYMMDD.dump /tmp/r.dump && sudo docker compose exec -T db pg_restore -U ragoh -d ragoh --clean < /tmp/r.dump` |
| Rotate a password | Change the value in Parameter Store, then re-run the Deploy workflow (admin/demo passwords only apply when the user is first created; use `POST /api/v1/users/{id}/reset-password` for existing users) |
| Use your own domain | Point a DNS A record at the server IP, set `domain_name` in `infra/terraform/envs/staging/variables.tf`, merge |
| Lost or stolen phone | Dashboard → **Phones** → **Block…** (tick **Also erase it**). The phone is signed out at once; it erases itself the next time it is online. Recorded in the audit log. |
| Who looked at whose data | Dashboard → **Audit log** (managers/admins) → "Access to personal data" |
| Retention | Nightly at 02:45: GPS points older than 90 days, device events 180 days, notifications 60 days, audit log 2 years (campaign config `retention`). Stops and daily summaries are kept. |
| Change the privacy notice | Edit campaign config `privacy` (or the text in `backend/app/core/privacy.py`) and raise `notice_version`: every user must accept again at their next sign-in or unlock |
| Logs as JSON | The API writes one JSON object per line (`RAGOH_LOG_JSON=true`): `docker compose logs api \| grep '"level": "ERROR"'` |
| Crash reporting (optional) | Server errors: put a Sentry DSN (sentry.io or self-hosted) in Parameter Store `/ragoh/staging/SENTRY_DSN` and redeploy; request bodies, headers and users are stripped before sending. Phone errors arrive as "app_error" events: crash count per phone on the **Phones** page. |
| Battery and data use | Dashboard → **Phones** (from each phone's end-of-shift report); method in `docs/MEASUREMENTS.md` |
| Integrations | Dashboard → **Integrations** (admins): status, errors, run now, settings; secrets in Parameter Store. Logs: `/var/log/ragoh-integrations.log`. Setup in `docs/INTEGRATIONS.md` |
| Load test | On a scratch database only: `uv run python -m app.perftest --api http://localhost:8000 --collectors 1000` (then `--cleanup`) |
| Stop paying for staging | Stop the instance in the EC2 console (≈ only disk and IP are charged while stopped), or ask Claude to add a schedule |

## Signing the Android app (recommended before handing phones out)

Without a release key, the APK is signed with Android's shared debug key: it installs fine, but anyone could build an "update" that Android accepts. With a release key, only your builds can update the app. **Keep the key safe: if it is lost, every phone must uninstall and reinstall to get updates.**

1. Create a keystore (any machine with Java, or a GitHub Codespace): `keytool -genkeypair -v -keystore ragoh-release.keystore -alias ragoh -keyalg RSA -keysize 4096 -validity 10000`
2. Save it somewhere safe (password manager or encrypted drive), then add three repository secrets (Settings → Secrets and variables → Actions):
   - `ANDROID_KEYSTORE_B64` — the file base64-encoded (`base64 -w0 ragoh-release.keystore`)
   - `ANDROID_KEYSTORE_PASSWORD` — its password
   - `ANDROID_KEY_ALIAS` — `ragoh`
3. Re-run the **Mobile** workflow; the summary says "APK signing: release key". Phones with a debug-signed app must uninstall it once before installing the release-signed one (sync first).

## Costs (estimate)

t3.small server ~USD 17/month, 30 GB disk ~USD 3, public IP ~USD 4, ECR/S3/SSM < USD 2. **About USD 25/month.** Routing and map data add well under USD 1/month in S3. The `ragoh-monthly` budget emails at 80% of USD 100.

> **AWS free plan:** if the first deploy fails at "Terraform apply" with an error about the instance type not being eligible, change `instance_type` in `variables.tf` to `t3.micro` (1 GB — tight but works for the pilot) or upgrade the account to a paid plan.
